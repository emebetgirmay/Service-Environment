# PRD: Observability Implementation Lab
Building a Modern MELT Operating Layer for 
Containerized Services
1\. Summary
Each group must add a modern observability layer to its existing Docker Compose-based service 
architecture.
The goal is to move from:
“Our services are running.”
to:
“Our services can be observed, tested, alerted on, traced, and debugged by another engineer.”
Each group will implement the **MELT model**:
**Signal** **Purpose**
Metrics Show service health, traffic, errors, and latency
Events Show important operational moments and changes
Logs Explain what happened inside each service
Traces Show the request journey across services
This is not a dashboard decoration assignment.
This is an operational visibility assignment.

4\. Required Open-Source Stack
4.1 Prometheus — Metrics
Prometheus must collect metrics from each service.
Each service must expose a Prometheus-compatible /metrics endpoint.
Prometheus must scrape services using Docker Compose service names, not hardcoded localhost 
assumptions.
--- Page 5 ---
Example:
scrape_configs:
  - job_name: "service-a"
    static_configs:
      - targets: ["service-a:3000"]
  - job_name: "service-b"
    static_configs:
      - targets: ["service-b:3000"]
  - job_name: "service-c"
    static_configs:
      - targets: ["service-c:3000"]
Prometheus must use a persistent named volume.
Example:
volumes:
  prometheus-data:
Why this matters:
Prometheus helps answer:
Is the service up?
How many requests are coming in?
How many requests are failing?
Is latency getting worse?
Did the service return to normal?

4.3 Jaeger — Distributed Tracing
Jaeger must be added for tracing.
Each service should emit trace spans. Where one service calls another, trace context should be 
propagated.
Minimum expected trace path:
gateway
   service-a
   service-b
   service-c
Each span should show:
service name
endpoint
duration
status
error state if failed
Required trace demo:
1\. Send a successful request through the gateway
2\. Open Jaeger
3\. Search by service name
--- Page 7 ---
4\. Show the full request journey
5\. Trigger a slow or failing endpoint
6\. Show where latency or failure appears in the trace
Why this matters:
Prometheus can show that latency increased. Jaeger helps show where the latency happened.
4.4 Logs — Structured Service Evidence
Each service must emit structured JSON logs.
Minimum request log:
{
  "timestamp": "2026-07-08T19:35:00Z",
  "service": "service-a",
  "level": "info",
  "method": "GET",
  "path": "/api/service-a",
  "status": 200,
  "duration_ms": 34,
  "request_id": "abc-123",
  "trace_id": "trace-123"
}
Minimum error log:
{
  "timestamp": "2026-07-08T19:36:00Z",
  "service": "service-b",
  "level": "error",
  "error": "dependency timeout",
  "request_id": "abc-123",
--- Page 8 ---
  "trace_id": "trace-123"
}
Required:
Every request has a request_id
Logs include service name
Logs include log level
Logs include request duration where applicable
Error logs are easy to identify
Trace ID is included where possible
Minimum acceptable log access:
docker compose logs service-a
Recommended:
Loki + Promtail for viewing logs inside Grafana
Why this matters:
Metrics show the symptom.
Traces show the path.
Logs explain the local detail.

4.6 Alerting — Detection Layer
Each group must define at least three alert conditions.
Required alerts:
**Alert 1: Service Down**
up{job="service-a"} == 0
**Alert 2: High Error Rate**
rate(http_errors_total[2m]) > 0.1
**Alert 3: High Latency**
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) 
> 0.5
Each alert must document:
Alert name
PromQL condition
What it means
Possible causes
How to reproduce it
First checks
How to confirm normal state
Minimum acceptable:
Prometheus alert rules with documented manual verification
Recommended:
Grafana alerts, Alertmanager, Slack, Discord, email, or webhook notification

Why this matters:
Humans should not discover service problems by accident. The system should expose meaningful 
failure conditions clearly.
5\. Service Instrumentation Requirements
Each service must implement these endpoints.
/health
Returns service health.
Example:
{
  "service": "service-a",
  "status": "ok",
  "dependencies": {
    "service-b": "ok"
  }
}
If a dependency is unavailable:
{
  "service": "service-a",
  "status": "degraded",
  "dependencies": {
    "service-b": "unreachable"
  }
}
Why this matters:
Health checks help engineers and alerting systems distinguish between healthy, degraded, and failed 
states.
--- Page 11 ---
/metrics
Exposes Prometheus metrics.
Minimum required metrics:
http_requests_total
http_request_duration_seconds
http_errors_total
service_up
Recommended labels:
service
method
route
status_code
Bad metric:
requests_total
Better metric:
http_requests_total{service="service-a", route="/api/service-a", 
method="GET", status_code="200"}
Why this matters:
Labels help engineers isolate problems by service, route, method, or status code.

14\. Final Standard
By the end of this assignment, each group should understand this operating principle:
Metrics tell us something is wrong.
Logs explain what happened.
Traces show where it happened.
Events show what changed.
Alerts call attention to the issue.
The goal is not just to run containers.
The goal is to operate services with visibility and discipline.
